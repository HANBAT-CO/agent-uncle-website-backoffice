# Agent Uncle 앱 · 백오피스 호환성 정비

기준일: 2026-10-17. 이 문서는 현재 앱 소스와 대조해 구현한 백오피스 변경, 검증 범위 및 Supabase 운영 반영 결과를 기록한다.

## 대조 기준과 적용 범위

- 앱: `agent-uncle/lisbon` 작업 디렉터리, 기준 커밋 `8e40220` 및 해당 작업 트리의 미커밋 변경사항.
- DB: 앱 마이그레이션 28개, `202610110001_workspace.sql`부터 `202610160006_order_completion_confirmation.sql`까지. 파일별 SHA-256은 [`app-snapshot.json`](../supabase-local/app-snapshot.json)에 고정했다.
- 백오피스: 기존 운영자 계층 뒤에 [`20261017090000_app_compatibility.sql`](../supabase/backoffice/20261017090000_app_compatibility.sql)을 추가했다. 기존 마이그레이션 이력은 수정하지 않는다.
- 구현·회귀 검증 대상: 별도 로컬 Docker 스택 `agent-uncle-backoffice`, API `127.0.0.1:55321`. 앱 작업 디렉터리와 앱의 로컬 DB는 변경하지 않았다.
- 운영 반영 대상: 사용자의 명시적 요청에 따라 Supabase `Agent-Uncle` 프로젝트(`auicerytbhnqeakmkscs`, `ap-northeast-2`)에 아래 세 마이그레이션을 반영했다. 앱 작업 트리에 미커밋 파일이 포함된 출처와 실제 운영 반영 결과는 구분해 기록한다.

## 권한과 지급 조건

조회자는 허용된 메타데이터를 볼 수 있다. 계좌, 대화, 메모·문의 상세는 운영자 이상이 열람 사유를 입력해야 하며 감사 로그가 남는다. 서버는 허용된 필드만 반환하고, 푸시 토큰·세션·공급자 오류 원문 및 삭제된 대화 내용은 반환하지 않는다.

정산 버튼은 **은행 송금을 실행하지 않는다**. 실제 은행 거래내역을 대조한 뒤 확인·반려·지급 완료를 기록한다. 클라이언트 표시와 별개로 DB에서 다음 조건을 다시 검증한다.

- 관리자 권한과 유효한 사유, 대상 레코드 버전, 금액 일치.
- 동일 작업의 재시도는 중복 반영하지 않고, 다른 요청이 같은 작업 ID나 은행 확인 번호를 재사용하면 거절.
- 삼촌 지급은 모든 연결 요청의 수령 완료, 유효한 수취 계정·계좌, 양수의 확정 금액, 충분한 운영 계좌 확인 입금액이 필요.
- 미확인 입금, 열린 문의, 누락 금액, 환불 필요, 재정산, 이미 완료된 지급은 지급을 차단. 삼촌에게 직접 입금된 금액은 운영 계좌 잔액으로 계산하지 않음.
- 앱과 같은 계정 생명주기/업무 잠금 순서를 지키고 상태 변경과 감사 기록을 같은 트랜잭션에 저장.

팀·편의·탈퇴·푸시·앱 릴리스 화면은 조회와 진단 범위다. 사용자 대신 협의를 수락하거나 업무를 인계하는 기능, 탈퇴 큐 강제 삭제, 푸시 강제 재발송, 릴리스 작성은 추가하지 않았다. 해당 동작은 앱의 참가자 권한 및 별도 처리기 규칙을 따른다.

앱 릴리스는 공통 조건과 플랫폼별 재정의 값을 구분해서 보여준다. 공통 공개 조건을 먼저 검사하고 플랫폼 값을 병합한 뒤 다시 검사하는 앱 규칙을 안내하며, 특정 사용자에게 실제 노출된다는 판정은 하지 않는다. 실제 업데이트 안내는 계정 상태·역할·대상 지정·공개 시각·설치 빌드·공식 스토어 주소에 따라 달라진다.

## Supabase 운영 반영 결과

2026-10-17 운영 프로젝트의 마이그레이션 이력에서 앱 `202610160004`까지의 선행 이력과 기존 랜딩·백오피스 계층을 확인했다. 함수 정의와 실행 권한을 로컬 검증본과 대조하고, 변경 대상 함수의 기존 정의·권한을 복구 자료로 보관한 뒤 다음 SQL과 이력을 한 트랜잭션으로 반영했다.

| 마이그레이션 | 반영한 원본 SHA-256 |
|---|---|
| `202610160005_wholesaler_batch_proposals.sql` | `01d30ec1ce33d889bcf18d4b433fb95d80000cb11cbe0069cd76601b3a0c4236` |
| `202610160006_order_completion_confirmation.sql` | `a6a20b611202119f3cebdb66f09b4c45660d9560597c7dc75da84c4317cdebe6` |
| `20261017090000_app_compatibility.sql` | `bf8f28ce30ee862a8e98b713545356027f1386ceb524efe778459eed32d16ec7` |

사전 확인 이후 이력·함수 변경 여부를 검사하고 잠금 및 실행 제한 시간을 적용했다. `202610160006`의 일부 함수는 이미 같은 정의였으나 이력이 없어, 재적용 가능한 정의를 확인한 뒤 원본 SQL과 함께 정확한 이력을 남겼다. 기존 이력은 덮어쓰지 않았다. 함수·권한·마이그레이션 이력만 변경했으며 고객 데이터나 운영 테스트 계정은 생성하지 않았다. 완료 후 PostgREST 스키마 캐시 갱신을 요청했다.

운영 반영 뒤 확인한 결과:

- 앱·백오피스 함수 **282개**의 정의 해시, 보안 정의자 설정 및 `anon`/`authenticated`/`service_role` 실행 권한이 로컬 검증본과 모두 일치.
- 새 이력 세 건에 저장한 원본 SQL 해시가 위 파일과 일치.
- [`hosted_checks.sql`](../supabase/backoffice/hosted_checks.sql)의 읽기 전용 검사 통과: 신규 RPC 9개의 존재·권한·안전한 검색 경로, 비공개 헬퍼 및 서비스 결제 함수 접근 제한, 관련 테이블 RLS, 감사 로그 해시 체인, 기존 요청의 상태 표시.
- 운영자 신원이 없는 `authenticated` 세션에서 신규 RPC **9개 모두 접근 거절** 확인. 운영자 계정 대행이나 실제 입금·지급 변경 없이 검사.

이 비교는 명시한 함수·권한·이력 및 읽기 전용 검사 범위다. 과거 28개 마이그레이션 모두의 원본 SQL이 운영 이력과 바이트 단위로 같다는 주장이나, 전체 운영 데이터의 업무 적합성 검사는 아니다. 기존 Supabase 프로젝트는 반영 후 `ACTIVE_HEALTHY` 상태였다.

## 웹 배포 후 확인 사항

대응하는 웹 버전은 새 RPC가 있는 DB를 요구한다. 운영 웹 배포 완료는 이 보고서의 검증 범위에 포함하지 않는다. 웹 배포 뒤 요청 조회, 입금 확인 화면, 정산 계좌 열람, 팀 대화 권한을 점검한다. 이전 백오피스 SQL만 재적용하면 최신 명령 래퍼를 덮어쓸 수 있으므로 사용하지 않는다.

이 웹 저장소에서 운영 프로젝트를 대상으로 `db push`나 `db reset`을 실행하지 않는다. 마이그레이션 소유권과 상세 절차는 [`supabase/README.md`](../supabase/README.md)에 정리했다.
