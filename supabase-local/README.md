# supabase-local: local Supabase for backoffice development

A local copy of the 사입삼춘 (Agent Uncle) database, used to build and test the backoffice under
`/admin`. It runs in Docker (OrbStack) and is **never linked to the live project**
`auicerytbhnqeakmkscs`. Nothing in this folder writes to the live project. The only live access is
`scripts/verify-schema.mjs`, which sends one read-only `SELECT` to the Management API.

| | |
|---|---|
| API (REST, Auth, Storage, Realtime) | http://127.0.0.1:55321 |
| Studio | http://127.0.0.1:55323 |
| Mailpit (local auth mail) | http://127.0.0.1:55324 |
| Postgres | `postgresql://postgres:postgres@127.0.0.1:55322/postgres` |
| CLI | `npx supabase@2.120.0` (the version the app docs recommend), always run through `scripts/sb.sh` |
| Docker project id | `agent-uncle-backoffice` (containers `supabase_*_agent-uncle-backoffice`) |

The app's own local stack (`lisbon`, ports 543xx) belongs to another workspace and keeps running
next to this one. This stack uses 553xx, so the two never collide. `scripts/sb.sh` refuses
`--all`, `--project-id`, `--linked`, `--db-url`, `link`, `db push` and other hosted-platform
commands, so a stop or reset here cannot reach the app stack or the live project.

## Commands

Run them from the repo root. Each one is a small script in `scripts/`.

| What | Command |
|---|---|
| Start (idempotent; uses pinned service versions, applies platform parity, writes env files) | `supabase-local/scripts/start.sh` |
| Stop (data volumes are kept) | `supabase-local/scripts/stop.sh` |
| Stop and delete this stack's data | `supabase-local/scripts/stop.sh --no-backup` |
| Status and keys | `supabase-local/scripts/sb.sh status` |
| **Reset and reseed** (db reset → migrations → platform parity → demo seed → staff seed → summary) | `supabase-local/scripts/reset.sh` |
| Reset to an empty schema (no demo data, no staff) | `supabase-local/scripts/reset.sh --empty` |
| Seed only (needs an empty DB, e.g. after `reset.sh --empty`) | `node supabase-local/seed/demo.mjs`, then `node supabase-local/seed/backoffice-staff.mjs` |
| Staff logins and sample staff activity only (idempotent, safe to re-run) | `node supabase-local/seed/backoffice-staff.mjs` |
| Demo data summary (status labels, invariants, counts) | `supabase-local/scripts/summary.sh` |
| Historical schema comparison with live (read-only; see limitations below) | `node supabase-local/scripts/verify-schema.mjs` |
| API checks (logins, RLS, storage, leads, backoffice layer) | `node supabase-local/scripts/check-api.mjs` |
| Backoffice pgTAP (261 tests across two files, rolled back) | `supabase-local/scripts/sb.sh test db` |
| Backoffice behaviour checks (153 checks on the demo data, rolled back) | `supabase/backoffice/run-checks.sh` (`--app <dir>` also runs the app's pgTAP files with the layer applied) |
| Current app pgTAP suites against this local stack | `supabase/backoffice/run-checks.sh --app <agent-uncle>/supabase/tests` |
| Check copied migrations against their sources | `supabase-local/scripts/sync-migrations.sh` (`--copy` to pull changes) |
| Regenerate the backoffice `Database` type (with its header line, see "Backoffice layer") | `{ echo '// generated by WP-01; regenerate after any backoffice SQL change'; supabase-local/scripts/sb.sh gen types typescript --local --schema public; } > src/lib/admin/database.types.ts` |
| psql inside the db container | `supabase-local/scripts/psql.sh` (or `-c "select ..."`) |

A full `reset.sh` takes about 40 seconds.

Staff are the rows of `public.backoffice_admins` (spec D3), all with `require_mfa = false` and a
confirmed email. `seed/demo.mjs` creates `admin@`; `seed/backoffice-staff.mjs` creates the other
three and upserts the staff rows through `psql.sh`, the same way the first owner is seeded on live
from the SQL editor. `admin@` still carries `app_metadata.backoffice_role = "admin"` from the demo
seed, but the backoffice ignores `app_metadata`.

Staff have **no app account**: they never call `bootstrap`, `saip_command` rejects them, and RLS
shows them **no** `saip_records` (those are visible only to their `readers`). Staff read and write
only through the `SECURITY DEFINER` `backoffice_*` RPCs of the backoffice layer (see "Backoffice
layer"), each of which starts with `require_admin()`. There is no service-role key on the web side.

## Demo data

`seed/demo.mjs` writes every business record through the real `saip_command` RPC. Each call is
signed in as the user who would make it in the app: the retailer sends, receives, reports and
answers; the 사입삼촌 accepts, records results, delivers and corrects. Business documents and
photos are uploaded to the private `saip-attachments` bucket through Storage. All the server
checks therefore hold, exactly as in production: 수령 ≤ 전달 ≤ 확보, versions, roles, held stock,
the proposal and issue rules, and the participant trigger.
`summary.sh` re-checks the quantity bounds (expect 0 violations).

  1 rejected, 1 withdrawn. Three 사입삼촌 have renewed invite codes; the other codes have expired.
- **64 requests** (61 상품별 요청 + 3 도매처 주문서, `requestType: "wholesaler"` from `202610130004`), covering every

The received label now follows the app payment projection; elapsed days do not turn an order into a paid order. Product amounts use 장 and wholesaler amounts use 건, including mixed-list totals.

- 34 deliveries (27 received, 7 awaiting receipt), 29 receipts (4 confirmations with a difference,
  2 corrections), 8 issues, 13 proposals (pending, approved, rejected and withdrawn), 3 drafts,
  65 attachments (generated PNG garment drawings marked DEMO, and PDF/PNG business documents
  marked "DEMO ONLY").
- About 340 chat messages (business-record cards plus free chat, a few with photos; one edited and
  one deleted through the message menu of `202610130000`) and about 390 notices. Older ones are read through `readNotice` and `markChatRead`; recent ones stay unread.
- **15 landing_leads**, inserted with the publishable key exactly like the landing's server
  action: 13 normal `landing-signup` rows (retailer, 사입삼촌 and other roles; with and without
  utm), 1 `landing-signup:timing-suspect` and 1 `e2e` row (`e2e-check@invalid`).

**Simulated time.** Steps run in chronological order: signups about 8 weeks ago, connections
5 to 6 weeks ago, requests over the last 4 weeks, the newest an hour ago. Because the RPC stamps
`clock_timestamp()`, one local SQL pass afterwards maps each operation's real time onto its
simulated time. It moves every `createdAt`, `updatedAt`, `correctedAt` and `receivedAt` (including inside
event `before`/`after`), `editedAt`, `deletedAt`, `codeExpires`, `saip_records.updated_at`, `saip_private.operations.created_at`,
`auth.users` and `auth.identities` times, storage object times and `landing_leads.created_at`.
Only timestamps move; no business field is written outside the RPC. Recheck dates are relative
to the day you run the seed, so "미송 재확인" stays correct after a reset on another day.

Record IDs are random UUIDs, so they change on every reset. Find records by product, store or
status instead (Studio, `summary.sql`, `psql.sh`).

**Staff activity.** `seed/backoffice-staff.mjs` then signs in as the operator and the owner with the
publishable key and writes through the real backoffice RPCs, so every row has its hash-chained
audit entry (8 rows after a reset):

- 2 operator notes on requests (the oldest 문제 확인 중 and 미송 재확인 requests)
- 1 open case, severity high, assigned to the operator, on the same 문제 확인 중 request
- 2 lead statuses on the two oldest real leads: `contacted` and `qualified`
- 2 notices for 소매업자: one draft (operator) and one live `info` notice (owner)
- `feature_flags` `{"newRequest": true}` (owner)

Reruns replay the same operation ids, so nothing is written twice. A rerun reuses the targets of
the earlier writes (read from the audit log through `psql.sh`), so it stays a replay even after
tests changed request labels or lead statuses. The script finishes by checking
all four logins and `backoffice_verify_audit_chain()` as the owner.

## App snapshot and backoffice migrations

plus `landing_leads` and two canonical backoffice migrations. The app source was
`/Users/edmond104/conductor/workspaces/agent-uncle/lisbon` at commit `8e40220`, **including uncommitted
working-tree migrations**. [`app-snapshot.json`](app-snapshot.json) records their SHA-256 hashes.
This is a source snapshot for compatibility testing, not evidence of what is deployed.

Canonical backoffice SQL lives in `../supabase/backoffice/`:

- `20261013090000_backoffice_admin_layer.sql`: original staff, audit and console layer. Existing
  deployment notes record its application on 2026-10-14; its hosted history row was verified on 2026-10-17.
- `20261017090000_app_compatibility.sql`: request/payment projections, safe workflow reads,
  receipt confirmation/rejection and payout recording, team conversations, lifecycle, push and app release diagnostics.
  Applied and verified locally, then applied to the hosted project on 2026-10-17 with the missing

`sync-migrations.sh` checks every copied migration and `--copy` refreshes them. On a new local
stack, use `reset.sh`; when iterating on the compatibility SQL, apply that file to this local stack
with `scripts/psql.sh`. Do not reapply the old baseline alone after current app migrations: it
replaces command wrappers. The check runner applies both backoffice layers in order, twice, inside
one rolled-back transaction to verify repeatability.

  `!.env.backoffice.local.example` to `.gitignore`.

## Live comparison limitations

The explicitly authorized 2026-10-17 rollout applied three reviewed migrations to the hosted
project and verified 282 function definitions and execution permissions against this isolated
stack. Read-only hosted checks also passed for RPC access, RLS, audit integrity and request
projections. See the [rollout report](../docs/app-compatibility-2026-10-17.md) for scope and hashes;
this is not a claim that all production data or historical migration sources were verified.
`scripts/verify-schema.mjs` is an optional read-only Management API comparison for an older
baseline. Its exclusions for pending backoffice objects, migration history and platform objects
are historical assumptions. A successful result from that script is **not proof of current live
parity**. Refresh the comparison rules against the actual deployed app history before using it
as release evidence. The current hosted checks live in `../supabase/backoffice/hosted_checks.sql`.

The local platform trigger and pinned service versions reproduce the earlier environment;
they do not assert the current production versions. Credentials used by the optional comparison
are read from the environment/keychain and must never be logged.

## Troubleshooting

- **"local database is not empty"**: the seed only runs on a fresh DB. Use `reset.sh`.
- **Port already in use**: check with `lsof -nP -iTCP:55321-55329 -sTCP:LISTEN`. Change the
  ports in `supabase/config.toml` and the URL guard in `scripts/write-env.mjs`, `seed/demo.mjs`,
  `scripts/check-api.mjs` and `scripts/smoke.py`.
- **`supabase start` after a Docker restart** just brings the containers back with their data.
- **The app's local stack** (`supabase_*_lisbon`) is someone else's. Never stop it, reset it or
  run `supabase stop --all`.
