# supabase-local: local Supabase for backoffice development

A local copy of the 사입삼춘 (Agent Uncle) database, used to build and test the backoffice under
`/admin`. It runs in Docker (OrbStack) and is **never linked to the live project**
`auicerytbhnqeakmkscs`. Nothing in this folder writes to the live project. The only live access is
`scripts/verify-schema.mjs`, which sends one read-only `SELECT` to the Management API.

| | |
|---|---|
| API (REST, Auth, Storage, Realtime) | http://127.0.0.1:55321 |
| Studio | http://127.0.0.1:55323 |
| Mailpit (local auth mail) | http://127.0.0.1:55324 |
| Postgres | `postgresql://postgres:postgres@127.0.0.1:55322/postgres` |
| CLI | `npx supabase@2.120.0` (the version the app docs recommend), always run through `scripts/sb.sh` |
| Docker project id | `agent-uncle-backoffice` (containers `supabase_*_agent-uncle-backoffice`) |

The app's own local stack (`lisbon`, ports 543xx) belongs to another workspace and keeps running
next to this one. This stack uses 553xx, so the two never collide. `scripts/sb.sh` refuses
`--all`, `--project-id`, `--linked`, `--db-url`, `link`, `db push` and other hosted-platform
commands, so a stop or reset here cannot reach the app stack or the live project.

## Commands

Run them from the repo root. Each one is a small script in `scripts/`.

| What | Command |
|---|---|
| Start (idempotent; pins service versions to live, applies platform parity, writes env files) | `supabase-local/scripts/start.sh` |
| Stop (data volumes are kept) | `supabase-local/scripts/stop.sh` |
| Stop and delete this stack's data | `supabase-local/scripts/stop.sh --no-backup` |
| Status and keys | `supabase-local/scripts/sb.sh status` |
| **Reset and reseed** (db reset → migrations → platform parity → demo seed → staff seed → summary) | `supabase-local/scripts/reset.sh` |
| Reset to an empty schema (no demo data, no staff) | `supabase-local/scripts/reset.sh --empty` |
| Seed only (needs an empty DB, e.g. after `reset.sh --empty`) | `node supabase-local/seed/demo.mjs`, then `node supabase-local/seed/backoffice-staff.mjs` |
| Staff logins and sample staff activity only (idempotent, safe to re-run) | `node supabase-local/seed/backoffice-staff.mjs` |
| Demo data summary (status labels, invariants, counts) | `supabase-local/scripts/summary.sh` |
| Compare schema with live (read-only; the backoffice layer is listed as pending) | `node supabase-local/scripts/verify-schema.mjs` |
| API checks (logins, RLS, storage, leads, backoffice layer) | `node supabase-local/scripts/check-api.mjs` |
| Backoffice layer pgTAP (158 tests, self-contained, rolled back) | `supabase-local/scripts/sb.sh test db` |
| Backoffice behaviour checks (131 checks on the demo data, rolled back) | `supabase/backoffice/run-checks.sh` (`--app <dir>` also runs the app's pgTAP files with the layer applied) |
| App smoke test (copy of the app's `tool/backend/smoke.py`) | `uv run --no-project python3 supabase-local/scripts/smoke.py` on a fresh DB (`reset.sh --empty`), then `reset.sh` |
| App pgTAP suite (97 tests, rolled back) | copy `<app>/supabase/tests/*.sql` to a temp dir, then `supabase-local/scripts/sb.sh test db <dir>/*.sql` |
| Check copied migrations against their sources | `supabase-local/scripts/sync-migrations.sh` (`--copy` to pull changes) |
| Regenerate the backoffice `Database` type (with its header line, see "Backoffice layer") | `{ echo '// generated by WP-01; regenerate after any backoffice SQL change'; supabase-local/scripts/sb.sh gen types typescript --local --schema public; } > src/lib/admin/database.types.ts` |
| psql inside the db container | `supabase-local/scripts/psql.sh` (or `-c "select ..."`) |

A full `reset.sh` takes about 40 seconds.

Staff are the rows of `public.backoffice_admins` (spec D3), all with `require_mfa = false` and a
confirmed email. `seed/demo.mjs` creates `admin@`; `seed/backoffice-staff.mjs` creates the other
three and upserts the staff rows through `psql.sh`, the same way the first owner is seeded on live
from the SQL editor. `admin@` still carries `app_metadata.backoffice_role = "admin"` from the demo
seed, but the backoffice ignores `app_metadata`.

Staff have **no app account**: they never call `bootstrap`, `saip_command` rejects them, and RLS
shows them **no** `saip_records` (those are visible only to their `readers`). Staff read and write
only through the `SECURITY DEFINER` `backoffice_*` RPCs of the proposed layer (see "Backoffice
layer"), each of which starts with `require_admin()`. There is no service-role key on the web side.

## Demo data

`seed/demo.mjs` writes every business record through the real `saip_command` RPC. Each call is
signed in as the user who would make it in the app: the retailer sends, receives, reports and
answers; the 사입삼촌 accepts, records results, delivers and corrects. Business documents and
photos are uploaded to the private `saip-attachments` bucket through Storage. All the server
checks therefore hold, exactly as in production: 수령 ≤ 전달 ≤ 확보, versions, roles, held stock,
the proposal and issue rules, and the participant trigger.
`summary.sh` re-checks the quantity bounds (expect 0 violations).

What a reset produces:

- **20 app accounts**: 12 소매업자, 6 사입삼촌 (one on 휴무), 2 unfinished signups.
- **23 connections**: 19 accepted, 2 pending (one from a retailer, one invitation from a 사입삼촌),
  1 rejected, 1 withdrawn. Three 사입삼촌 have renewed invite codes; the other codes have expired.
- **61 requests**, covering every label of the app's `RequestRecord.statusLabel`:

  |---|---|---|
  | 완료 | 11 | single delivery; back-order then a 2nd round; 2 split deliveries; short receipt → correction → issue resolved → final round; 2 requests in one batched delivery; back-order cancelled by agreement; over-receipt → correction; option changed after accept; damage reported → action → resolved |
  | 취소 종료 | 4 | cancelled before accept (×2); full cancel agreed after accept; cancel including already-secured stock |
  | 거절 | 4 | 단종, 최소 수량, 도매처 휴업, 휴가 |
  | 확인 대기 | 6 | incl. one edited before acceptance, one to the 사입삼촌 on 휴무 |
  | 진행 중 | 5 | accepted, no result yet |

  | 미송 재확인 | 4 | recheck date today or earlier; reminder notices from `refreshReminders` |
  | 미송 대기 | 3 | future recheck, incl. a partial delivery |
  | 픽업 완료 | 3 | secured, not delivered yet |

  | 문제 확인 중 | 5 | short receipt; damage after completion with 조치; short receipt with 조치; wrong colour with 5 held; issue on an unconfirmed delivery |

- 32 deliveries (25 received, 7 awaiting receipt), 27 receipts (4 confirmations with a difference,
  2 corrections), 8 issues, 13 proposals (pending, approved, rejected and withdrawn), 3 drafts,
  68 attachments (generated PNG garment drawings marked DEMO, and PDF/PNG business documents
  marked "DEMO ONLY").
- About 325 chat messages (business-record cards plus free chat, a few with photos) and about 370
  notices. Older ones are read through `readNotice` and `markChatRead`; recent ones stay unread.
- **15 landing_leads**, inserted with the publishable key exactly like the landing's server
  action: 13 normal `landing-signup` rows (retailer, 사입삼촌 and other roles; with and without
  utm), 1 `landing-signup:timing-suspect` and 1 `e2e` row (`e2e-check@invalid`).

**Simulated time.** Steps run in chronological order: signups about 8 weeks ago, connections
5 to 6 weeks ago, requests over the last 4 weeks, the newest an hour ago. Because the RPC stamps
`clock_timestamp()`, one local SQL pass afterwards maps each operation's real time onto its
simulated time. It moves every `createdAt`, `updatedAt` and `correctedAt` (including inside event
`before`/`after`), `codeExpires`, `saip_records.updated_at`, `saip_private.operations.created_at`,
`auth.users` and `auth.identities` times, storage object times and `landing_leads.created_at`.
Only timestamps move; no business field is written outside the RPC. Recheck dates are relative
to the day you run the seed, so "미송 재확인" stays correct after a reset on another day.

Record IDs are random UUIDs, so they change on every reset. Find records by product, store or
status instead (Studio, `summary.sql`, `psql.sh`).

**Staff activity.** `seed/backoffice-staff.mjs` then signs in as the operator and the owner with the
publishable key and writes through the real backoffice RPCs, so every row has its hash-chained
audit entry (8 rows after a reset):

- 2 operator notes on requests (the oldest 문제 확인 중 and 미송 재확인 requests)
- 1 open case, severity high, assigned to the operator, on the same 문제 확인 중 request
- 2 lead statuses on the two oldest real leads: `contacted` and `qualified`
- 2 notices for 소매업자: one draft (operator) and one live `info` notice (owner)
- `feature_flags` `{"newRequest": true}` (owner)

Reruns replay the same operation ids, so nothing is written twice. A rerun reuses the targets of
the earlier writes (read from the audit log through `psql.sh`), so it stays a replay even after
tests changed request labels or lead statuses. The script finishes by checking
all four logins and `backoffice_verify_audit_chain()` as the owner.

## Backoffice layer (proposed, local only)

The canonical migration is `../supabase/backoffice/20261013090000_backoffice_admin_layer.sql`. It is
**proposed**: it is not on live and ships only through the app repo (see
[`../supabase/README.md`](../supabase/README.md)). Locally it is the 8th migration,
`supabase/migrations/20261013090000_backoffice_admin_layer.sql`, a byte-for-byte copy;
`scripts/sync-migrations.sh` reports drift and `--copy` refreshes it. If the canonical file changes,
copy it, run `reset.sh`, then all of the checks below, then regenerate the types.

| Check | What it covers |
|---|---|
| `../supabase/backoffice/run-checks.sh` | 131 behaviour checks inside `BEGIN … ROLLBACK`, with the migration applied twice (idempotency): privileges, masking, audit throttling, storage gating, review, suspension, write freeze, replays, notices, config, staff, tamper and ledger-violation detection. Needs the demo seed. `--app <dir>` also runs the app's pgTAP files with the layer applied. |
| `supabase/tests/backoffice_test.sql` (`sb.sh test db`) | the pgTAP port of the same checks (158 tests). Self-contained: it builds its own app fixtures through `saip_command` and its own staff at fixed UUIDs (`@staff.test`), so it passes on `reset.sh --empty`, on the seeded DB and in the app repo next to its own tests. |
| `scripts/check-api.mjs` | through the real API: owner `backoffice_whoami` ready, all four logins, audit chain, a demo user gets 403 from `rpc/backoffice_overview`, anon 401/403, anon `rpc/app_bootstrap_config` 200 with `maintenance`, no REST access to `backoffice_audit_log`, and the staff seed's activity (its audit actions, `feature_flags.newRequest` in `app_bootstrap_config`, and the live notice, but not the draft, in a retailer's `app_bootstrap_config`). It writes nothing, so it adds no audit rows. |
| `scripts/verify-schema.mjs` | lists the layer under "pending, not on live" and still exits 0 when nothing else differs (see "Schema parity with live"). |

`src/lib/admin/database.types.ts` is generated from this DB. Its first line,
`// generated by WP-01; regenerate after any backoffice SQL change`, is added by hand after
`sb.sh gen types typescript --local --schema public`. CLI 2.120 prints the file unformatted; keep it
that way (no formatter pass) so a regeneration diff shows only real schema changes. Regenerating on
an unchanged schema gives a byte-identical file.

- The landing's `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` in `.env.local`
  still point at the **live** project and are not overridden (different variable names). The
  landing keeps working as before.
- `.env.development.local` is not loaded for `next build`/`next start` or under `NODE_ENV=test`.
  Production backoffice config is a later decision.
- No service-role or secret key ever goes into a Next.js env file. The local service-role key is
  only for the seed scripts.
- The example was meant to live at `/.env.backoffice.local.example`. The agent file-protector
  hook blocks agent writes to `.env.*` paths, so it sits here. To move it, run
  `cp supabase-local/env.backoffice.local.example .env.backoffice.local.example` and add
  `!.env.backoffice.local.example` to `.gitignore`.

## Schema parity with live

`scripts/verify-schema.mjs` runs `scripts/schema-fingerprint.sql` on both sides (local via psql,
live via `POST /v1/projects/auicerytbhnqeakmkscs/database/query/read-only`). It compares
schemas `public` and `saip_private`:

- tables and columns, defaults, constraints, indexes, RLS flags, table and column grants, triggers
- functions, by the md5 of `pg_get_functiondef`, `SECURITY DEFINER`, volatility, `search_path`
  and EXECUTE grants
- policies, including `storage.objects`
- the `saip-attachments` bucket, the `supabase_realtime` publication, event triggers, extension
  versions and the Postgres version

The access token comes from `$SUPABASE_ACCESS_TOKEN`, `~/.supabase/access-token` or the macOS
keychain item "Supabase CLI", and is never printed.

Result on 2026-10-13: everything identical apart from the pending backoffice layer. Postgres is
17.11 on both sides. Tables 3/3, functions 34/34, policies 5/5, bucket 1/1, event triggers 7/7,
publication `public.saip_records`.

Known, intentional differences:

1. **Migration history**: live records the 6 app migrations. Locally `20261011230000_landing_leads`
   is a 7th migration. On live it was applied through the SQL endpoint, outside the history
   (see `../supabase/README.md`).
2. **Platform event trigger `ensure_rls`** (`public.rls_auto_enable()`): live has this hosted
   platform feature, but it is not in any migration. `platform/rls_auto_enable.sql` reproduces it
   byte for byte. `start.sh` and `reset.sh` apply it after the migrations, and it is not a
   migration.
3. **Service versions**: `scripts/pin-versions.sh` writes `supabase/.temp/*-version`
   (gitignored) with the live versions: postgres 17.11.0.003, gotrue v2.197.0, postgrest v14.18
   and storage v1.80.2. The CLI uses these images. These are the same pins the app repo's
   linked `.temp` uses.
4. **Pending backoffice layer** (`20261013090000_backoffice_admin_layer`, proposed, local only).
   Its objects are printed under "pending, not on live" (50 on 2026-10-13) and are not mismatches:
   schema `backoffice_private` (checked locally; it is outside the fingerprint), the 9 tables
   `public.backoffice_*`, `app_remote_config` and `app_notices`, the functions
   `is_backoffice_admin`, `app_write_blocked`, `app_bootstrap_config` and `backoffice_*`, trigger
   `backoffice_guard_app_writes` and index `saip_records_collection_updated` on
   `public.saip_records`, storage policies `backoffice_attachment_read` and
   `app_attachment_write_guard`, and the migration version. An object counts as pending only while
   it exists locally and not on live; once the app repo ships the layer, the same objects are
   compared like everything else.

## Troubleshooting

- **"local database is not empty"**: the seed only runs on a fresh DB. Use `reset.sh`.
- **Port already in use**: check with `lsof -nP -iTCP:55321-55329 -sTCP:LISTEN`. Change the
  ports in `supabase/config.toml` and the URL guard in `scripts/write-env.mjs`, `seed/demo.mjs`,
  `scripts/check-api.mjs` and `scripts/smoke.py`.
- **`supabase start` after a Docker restart** just brings the containers back with their data.
- **The app's local stack** (`supabase_*_lisbon`) is someone else's. Never stop it, reset it or
  run `supabase stop --all`.
